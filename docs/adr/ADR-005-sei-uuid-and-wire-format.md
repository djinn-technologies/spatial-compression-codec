## Context

The SCC codec emits its compressed depth payload as the body of an H.264
`user_data_unregistered` SEI message (ISO/IEC 14496-10 §D.1.6). Three
interrelated decisions need to be locked before the codec can be wired
end-to-end:

1. **SCC SEI UUID** — every `user_data_unregistered` payload begins with a
   16-byte UUID identifying the format owner. The bytes need to be a real
   UUIDv4, not a placeholder; once committed, they are immortal in every
   SCC bitstream.
2. **Wire format** — exact byte layout, endianness, length prefixes, and
   how the variable-length quad-tree descriptor is delimited.
3. **Demux validation order** — the demuxer is a *parser of attacker-
   controlled bytes* once the format ships. It must reject malformed
   inputs without crashing, allocating multi-gigabyte buffers from a
   single forged length field, or reading past its input.

## Decision

### 1. UUID = `5cc1d4e7-7e93-4b51-9d3c-fa20b8167a45` (UUIDv4)

Bytes (in wire order):

    5c c1 d4 e7  7e 93  4b 51  9d 3c  fa 20 b8 16 7a 45

UUIDv4 conformance:

- Byte 6 = `0x4b` — high nibble `4` → version 4 marker. ✓
- Byte 8 = `0x9d` — high two bits `10` → variant DCE 1.1. ✓

Provenance: pulled from a UUIDv4 entropy source on 2026-05-06 specifically
for this project; not derived from a name. **MUST NOT change** without
bumping the format version (which would cause every existing decoder to
reject the new bytestream — a deliberate signal to ops).

The UUID is exported as `scc::sei::kSccSeiUuid` from
`codec/include/scc/sei.hpp`. Decoders verify the first 16 bytes of the
SEI payload against this constant; non-SCC `user_data_unregistered`
messages produced by other vendors are rejected gracefully.

### 2. Wire format

Big-endian for every multi-byte integer. The full layout (RBSP, before
the §7.4.1.1 emulation-prevention transformation) is documented in
`codec/src/common/sei/README.md` with an annotated hex example. Key
choices:

- **u32 length prefixes** for the three rANS streams. uint32 caps at
  4 GiB, well above the 256 MiB cap, and lets the demuxer skip an
  unknown-tail in a future format minor bump.
- **No length prefix on `quadtree_descriptor`.** The descriptor consumes
  the rest of the SEI payload. The H.264 outer SEI envelope provides the
  exact byte boundary, so an internal length prefix would be redundant.
  This choice is friendly to the codec's I-frame case where the descriptor
  is a single byte and a u32 prefix would be 80% overhead.
- **`top` array is fixed size 16 with 16-bit entries**, but the wire
  format only writes the first `top_count` of them. Slots
  `[top_count, 16)` are zeroed by the demuxer on reconstruction. This
  keeps payload size minimal for the typical `top_count = 4` case
  (2 bytes per skipped slot saved).
- **Endianness via raw byte arithmetic.** No `htonl` / `htons`. The
  `read_u16_be / write_u32_be` helpers are platform-independent and work
  identically on big-endian hosts where `htonl` would be a no-op.

### 3. Demux validation order

The demuxer follows a strict three-step gate:

1. **Input cap.** `sei_payload.size() > max_payload_bytes` ⇒
   `{ok = false}` immediately, no allocation. Default cap is 256 MiB
   (overridable per call).
2. **De-escape.** `nal_unescape` allocates one buffer of size
   ≤ `input.size()` (de-escape never grows). The intermediate RBSP is
   itself bounded by the cap.
3. **Per-field bounds.** For each `u32` length field, the demuxer reads
   the value and *then*:
   - rejects if `len > max_payload_bytes`;
   - rejects if `len > bytes_remaining_in_rbsp`;
   - *only then* calls `vector::assign(p, p + len)`.

A malicious payload claiming `rans_top_len = 0xFFFFFFFF` in a 50-byte
SEI message is rejected at step 3 before any vector resize. Test S6 in
`test_sei.cpp` constructs exactly this attack and asserts `ok == false`.

Test S5 enumerates *every* prefix of a known-good payload and confirms
the demuxer rejects all of them — a stronger property than "doesn't
crash" because it also pins the rejection contract. Test S11 throws
arbitrary rapidcheck-generated bytes at the demuxer (the portable fuzz
gate); the libFuzzer harness in `codec/fuzz/fuzz_sei.cpp`
(`SCC_ENABLE_LIBFUZZER=ON`) extends this to coverage-guided nightly
fuzzing under Clang.

## Consequences

### Positive

- One canonical UUID identifies SCC streams unambiguously across
  vendors. A non-SCC `user_data_unregistered` message wrapped in
  `scc::sei::demux` is rejected at the very first 16-byte memcmp.
- The wire format is fully big-endian and platform-independent. There
  is no host-byte-order handshake.
- The demux validation order is the load-bearing security invariant
  for a parser of network-attacker-controlled bytes. It is exercised
  by S5 / S6 / S11 in the unit tests, and by libFuzzer under
  `SCC_ENABLE_LIBFUZZER`.

### Negative

- The `kSccSeiUuid` value is now part of the wire format and cannot be
  changed without breaking every existing stream. Mitigated by
  documentation in this ADR and an inline comment on the constant.
- The "quadtree consumes the rest" rule means a future minor version
  cannot append a new optional field after the descriptor. If the
  format needs forward extension, version_minor will be bumped and a
  *new* length prefix introduced (the major bump path). This trade was
  taken for I-frame size efficiency.

### Deferred

- **Real-libavcodec round-trip test (Ultrathink #5).** Wraps the EBSP
  output in a real H.264 SEI NAL, writes a frame via libavcodec, reads
  it back, extracts the SEI payload, demuxes. Requires `libavcodec` as
  a dependency for one test — disproportionate for this milestone.
  Documented as a v1-release gate in `docs/Test_Plan.md`.
- **C ABI surface.** The mux/demux are C++17 today. The cabi/ shim
  prompt will expose them as opaque-ptr C functions; the wire format
  this ADR locks is what crosses the ABI.
- **Multi-message SEI NAL.** A single H.264 SEI NAL can contain
  multiple SEI messages. The current contract is one SCC payload per
  NAL; the codec layer's NAL writer is responsible for ensuring that.
  If we ever need to coexist with other SEI types in the same NAL, the
  caller will pre-extract the SCC message body and pass it to demux.

## Verification

- `codec/tests/test_sei.cpp` cases S1–S12 cover every behaviour
  documented in this ADR: round-trips (S1, S2, S12), NAL escape
  invariants (S3, S4), truncation (S5), oversized-length attack (S6),
  contract violations (S7–S9), input cap (S10), and arbitrary-bytes
  fuzz (S11).
- `codec/fuzz/fuzz_sei.cpp` is the libFuzzer entry point.
  `SCC_ENABLE_LIBFUZZER=ON` builds it under Clang/clang-cl with
  `-fsanitize=fuzzer,address,undefined`.
- `codec/src/common/sei/README.md` documents the wire format with the
  byte-by-byte hex example for ops debugging.
- File header in `sei.hpp` cites `[REQ-013]`, `[REQ-014]`,
  `[ISO/IEC 14496-10 §D.1.6]`, `[ISO/IEC 14496-10 §7.4.1.1]` with the
  ITU-T H.264 spec URL.

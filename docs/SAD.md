## 1. Executive Summary

The Spatial Compression Codec (**SCC**) is a depth-aware codec, multi-language SDK, and reference application family commissioned by Djinn Technologies Ltd. for use in 3D-video streaming, recording, and volumetric visualisation. The codec implements the techniques disclosed in **US Patent 10,827,161 B2** ("Method for Real-Time Compression of 3D Video Streaming Frames") [US10827161B2], which Djinn Technologies Ltd. owns following its acquisition of EF EVE Ltd. The system is designed to compress the depth channel that accompanies RGB video in RGB-D pipelines, while leaving RGB compression to the existing H.264/AVC framework — the compressed depth payload travels in-band as a `user_data_unregistered` SEI message [REQ-013, ISO/IEC 14496-10 §D.1.6].

In one sentence: **SCC compresses depth video by row-prefix differencing, splits the resulting disparity matrix into a small high-frequency "TOP" alphabet plus a remainder, encodes both with a Range Asymmetric Numeral Systems (rANS) entropy coder, applies pixel-level interlacing in regions detected as low-motion via a quad-tree, and packs the output into H.264 SEI NAL units so a single bitstream carries both colour and depth.**

### Top architectural facts (each cited; see §15 for risks)

1. The codec performs row-based difference encoding to expose redundancy where adjacent rows of depth are similar [US10827161B2 col. 4–5; REQ-002].
2. Backend entropy coding uses Range Asymmetric Numeral Systems with two alphabets — 8-bit for the TOP and B lists, 16-bit for the R list [US10827161B2 col. 7–8; REQ-007, REQ-009; Duda 2014].
3. Movement-aware pixel interlacing is driven by a quad-tree region map and per-region update bitmasks (e.g. `10110111`) [US10827161B2 col. 9–10; REQ-004, REQ-021, REQ-022].
4. Compressed depth payloads are carried as H.264 `user_data_unregistered` SEI messages, preserving compatibility with the existing H.264 ecosystem [REQ-013, REQ-014; ISO/IEC 14496-10 §D.1.6].
5. The codec must sustain ≥ 25 fps real-time throughput and exceed standard lossless algorithms by > 40 % compression ratio [REQ-016, REQ-017].

### Top three risks

| # | Risk | Severity |
|---|---|---|
| R-01 | rANS implementation correctness — the algorithm is sensitive to renormalisation and state-truncation off-by-one errors. Reference test vectors must be obtained or generated against a known-good rANS implementation before integration. | **High** |
| R-02 | H.264 SEI payload size limits and decoder leniency vary across hardware decoders (NVENC, QSV, Apple VT, Android MediaCodec). Some decoders silently strip unrecognised SEI types, breaking the depth path. | **High** |
| R-03 | Patent enforceability and prior-art exposure in jurisdictions where the patent is not registered (the patent is US-granted; equivalents in EU/UK/JP/CN are not represented in the brief). Strategic IP review required prior to international launch. | **Medium** |

Full risk register: §15.

## 4. Architecture Drivers

### 4.1 Quality goals (ranked)

1. **Functional correctness** — round-trip identity in lossless mode, bounded-error reconstruction in lossy mode.
2. **Real-time throughput** — ≥ 25 fps on commodity x86_64 hardware at 1280×720, 12 bpp [REQ-016].
3. **Compression efficiency** — > 40 % gain vs zlib/PNG/TIFF on representative depth streams [REQ-017, REQ-024].
4. **Visual fidelity under 3D operations** — no perceptible seams or banding under rotate/zoom of reconstructed point clouds [REQ-019].
5. **Portability** — single C ABI; bindings for WASM, Python, Unity, Unreal [REQ-026 .. REQ-029].
6. **Patent-defensibility** — implementation traceable to patent claims for licensing audits.
7. **Maintainability** — modular C++17 codebase, no proprietary upstream dependencies in the codec core.

### 4.2 Architecturally significant requirements

The full numbered REQ catalogue lives in `acceptance/Acceptance_Criteria.md`. The architecturally significant subset:

| ID | Requirement | Architectural Impact |
|---|---|---|
| REQ-001 | Process pixel-depth frames by encoding differences between neighbouring rows. | Drives `DisparityMatrixBuilder` component. |
| REQ-002 | Create disparity matrix S over consecutive rows. | Same. |
| REQ-003 | Use rANS for backend entropy compression. | Drives `rANS-8` / `rANS-16` components. |
| REQ-004 | Implement pixel-level interlacing based on motion. | Drives `MovementDetector`, `QuadTreeRegionMap`, `InterlacePatternSelector`. |
| REQ-013 | Package compressed depth as `user_data_unregistered` SEI in H.264. | Drives `SEIPayloadMuxer` component and the H.264 integration boundary. |
| REQ-016 | ≥ 25 fps real-time throughput. | Drives use of C++17 + SIMD hot paths, ring-buffer frame queue, optional GPU offload. |
| REQ-017 | > 40 % compression gain vs lossless baselines. | Drives the rANS choice and the TOP/R/B decomposition. |
| REQ-019 | Minimise rotation/zoom artefacts in reconstruction. | Drives interpolation strategy in the `PixelInterpolator` and the choice of motion thresholds. |
| REQ-026..029 | SDK bindings (WASM, Python, Unity, Unreal). | Drives existence of the stable C ABI as a separate container. |

### 4.3 Assumptions

- The H.264 elementary stream is muxed by a libavformat-equivalent that preserves SEI NAL ordering across the network/storage path.
- Depth sensors deliver depth aligned to the RGB frame (the agent does not undistort or re-register).
- The reference web app targets browsers with WebGPU and WebCodecs support (Chrome 113+, Edge 113+, Safari 17+, Firefox 122+ behind a flag at time of writing).
- AWS is the default cloud target for the reference deployment; the architecture is portable to GCP/Azure with equivalent services.

## 5. Solution Strategy

### 5.1 Technology decisions

| Layer | Technology | Rationale (cited) |
|---|---|---|
| Codec core | **C++17** | Required for SIMD intrinsics, deterministic bit-level layout, and footprint on embedded targets. |
| Build system | **CMake 3.27+** with **Conan 2** for dependency lock | Industry-standard for C++ libraries with cross-platform reach. |
| Entropy coder | **rANS** (custom C++17 impl, two state widths) | Mandated by patent and REQ-009/010. Reference: Duda 2014. |
| H.264 integration | **libavcodec / libavformat** (LGPL fork acceptable) | Mandated by REQ-013/014; libav is the canonical FFmpeg foundation. |
| C ABI shim | Hand-written C99 header + thin wrappers | Stable ABI is a hard requirement for SDK longevity (REQ-026). |
| WASM binding | **Emscripten** + custom TS facade | Browser delivery target; established toolchain. |
| Python binding | **pybind11** + NumPy zero-copy | Standard for scientific-Python interop. |
| Unity binding | **NativePlugin** (C# `[DllImport]` + IL2CPP) | Cross-platform via Unity's own packaging. |
| Unreal binding | **Unreal Plugin** (UPROPERTY + Blueprint nodes) | Same rationale. |
| Capture agent | **Rust 1.78+** | Memory safety at the sensor boundary, zero-cost FFI to libscc, single static binary. |
| Control-plane API | **Node.js 20 LTS + Fastify** | Lightweight; first-class TypeScript; well-supported by the wider Akuma stack. |
| Web frontend | **React 18 + TypeScript + Vite + Zustand + WebGPU** | Standard SPA stack at Akuma; WebGPU for the volumetric viewport. |
| Persistence | **PostgreSQL 16 (RDS)** + **Redis (ElastiCache)** | Mature, predictable, AWS-native. |
| IaC | **Terraform 1.7+** | Multi-cloud portability. |
| Observability | **OpenTelemetry** + **Grafana** | Vendor-neutral, supports all targets. |

### 5.2 Architectural patterns observed (planned)

- **Pipeline + filter** — encoder and decoder are linear pipelines of pure-function components; testable in isolation.
- **Strategy pattern** — interlace pattern selection, motion-threshold tuning, and rate-control all behind interfaces so they are profile-swappable at runtime.
- **C ABI as anti-corruption layer** — language bindings depend only on `libscc.h`, never on internal C++ types. This insulates the public surface from internal refactoring.
- **Clear-text in-band side channel** — depth payload rides H.264 SEI as a UUID-addressed unregistered payload, not a separate stream. Encryption (if required) wraps the whole bitstream.

### 5.3 Key design decisions (forward-looking ADRs)

These are anticipated architecture-decision records; each will be committed under `docs/adr/` once development starts.

- **ADR-001** — _Use rANS rather than arithmetic or Huffman coding_. Decision: rANS. Rationale: mandated by patent; competitive compression to arithmetic coding with Huffman-class decode speed (Duda 2014).
- **ADR-002** — _Two state widths (8-bit, 16-bit) for the rANS engine, not one_. Decision: two. Rationale: TOP/B alphabets are tiny (4 / 2 symbols) and benefit from 8-bit state; R alphabet is full int16 and needs 16-bit state to avoid renormalisation thrashing [REQ-009/010, US10827161B2 col. 7–8].
- **ADR-003** — _Quad-tree leaf size = 16×16 pixels_. Decision: 16×16. Rationale: matches macroblock size of H.264; cheap to align in SIMD loops; coarse enough to amortise the per-region pattern overhead.
- **ADR-004** — _Carry depth in H.264 SEI rather than in a separate substream_. Decision: SEI. Rationale: REQ-013/014; preserves single-bitstream simplicity; survives most muxing/demuxing pipelines unchanged.
- **ADR-005** — _Register a stable UUID for the SCC SEI payload_. Decision: yes; UUID is `e9c1f1a0-9c0d-4b87-9b5c-djinn-scc-2026` (placeholder; replace with cryptographically random 16-byte UUIDv4 at first commit). Stored once as a build-time constant.
- **ADR-006** — _Public language bindings depend on the C ABI only, never on the C++ headers_. Decision: yes. Rationale: ABI stability across compiler versions and STL implementations.
- **ADR-007** — _Lossy mode is achieved through a controlled increase of motion thresholds and reduction of TOP-list refresh rate, not through lossy quantisation of disparity values_. Decision: yes. Rationale: keeps the entropy back-end deterministic; lossiness is bounded by interlace skip probability rather than uncontrolled re-quantisation [REQ-012].

## 7. Component Architecture (C4 Level 3)

### 7.1 Encoder components

![Encoder components](diagrams/03_c4_l3_encoder.png)

*Figure 3 — Encoder pipeline. RGB is delivered separately to H.264; only the depth path is shown here. The pipeline is strictly forward-flowing, with the `RateController` adjusting the `DepthFilter` and `InterlacePatternSelector` based on profile.*

#### 7.1.1 `DepthFilter`
- **Purpose:** Smooth raw depth values; fill holes (zero pixels) caused by sensor occlusion or specular reflection [REQ-011].
- **Public methods:** `apply(DepthFrame& in_out, FilterMode mode)` where `mode ∈ { None, Median3, Median5, BilateralFast, HoleFillNN }`.
- **Default:** `Median3 + HoleFillNN`.
- **Evidence:** REQ-011.

#### 7.1.2 `BitDepthAdapter`
- **Purpose:** Quantise/clamp depth to the configured target bit-depth.
- **Modes:** 8 bpp (perceptual quantisation, lossy by definition), 12 bpp (recommended default), 16 bpp (lossless input pass-through).
- **Evidence:** REQ-005.

#### 7.1.3 `DisparityMatrixBuilder`
- **Purpose:** Compute matrix S per the patent formula.
- **Algorithm (canonical, do not deviate):**
  ```
  s[1,1] = d[1,1]
  for j = 2..W:    s[1,j]   = d[1,j]   - d[1,j-1]
  for i = 2..H:
    for j = 1..W:  s[i,j]   = d[i,j]   - d[i-1,j]
  ```
- **Evidence:** US10827161B2 col. 4–5; REQ-002, REQ-006.
- **SIMD plan:** vectorise the inner loop with AVX2 (Linux/Win x86_64) and NEON (ARM64).

#### 7.1.4 `FrequencyAnalyser`
- **Purpose:** Build the histogram of S, select the TOP-x most-frequent values, and split S into TOP, R, and B.
- **TOP cardinality:** default x = 4. Configurable in [2, 16]. The patent observes that x = 4 typically captures 85–98 % of disparity values [US10827161B2 col. 7].
- **Output:**
  - `TOP[k]` — array of top-x values (transmitted in the frame header).
  - For each pixel `(i,j)`:
    - if `S[i,j] ∈ TOP` → emit index in `top_indices` stream, set `B[i,j] = 0`.
    - else → emit value in `R` stream, set `B[i,j] = 1`.
- **Evidence:** REQ-007, REQ-008.

#### 7.1.5 `rANS-8 Encoder`
- **Purpose:** Compress `top_indices` (alphabet ≤ 256) and `B` (binary alphabet) using 8-bit-state rANS.
- **State width:** 32-bit accumulator with 8-bit renormalisation byte output.
- **Reference:** Duda 2014, §3.3 (rANS).
- **Evidence:** REQ-009.

#### 7.1.6 `rANS-16 Encoder`
- **Purpose:** Compress `R` values (full int16) using 16-bit-state rANS.
- **State width:** 32-bit accumulator with 16-bit renormalisation chunk output.
- **Evidence:** REQ-010.

#### 7.1.7 `MovementDetector`
- **Purpose:** Compute Δ = | f(n) − f(n-1) | per pixel.
- **Cache:** Holds the previous depth frame in a `FrameCache` (one-frame ring).
- **Evidence:** REQ-021.

#### 7.1.8 `QuadTreeRegionMap`
- **Purpose:** Recursively partition the frame into regions whose motion intensity is homogeneous.
- **Leaf size:** 16×16 px (ADR-003).
- **Classes:** `0 = static`, `1 = low-motion`, `2 = high-motion`. Thresholds `τ_static`, `τ_low`, `τ_high` are profile-tunable.
- **Evidence:** REQ-022.

#### 7.1.9 `InterlacePatternSelector`
- **Purpose:** Map each region's motion class to an 8-bit interlace bitmask.
- **Default mapping:**
  - Static → `11111111` _(in lossless mode; for lossy, cycle once every N frames as `10000000`)_
  - Low motion → `10110111`
  - High motion → `11111111`
- **Evidence:** REQ-021, US10827161B2 col. 9–10.

#### 7.1.10 `SEIPayloadMuxer`
- **Purpose:** Pack the encoded buffers into an H.264 SEI NAL.
- **Wire format:**
  ```
  [16 B SCC UUID]
  [u8 version_major][u8 version_minor]
  [u16 width][u16 height][u8 bit_depth][u8 mode_flags]
  [u8 top_count][u16 top_values × top_count]
  [u32 rans_top_len][bytes rans_top]
  [u32 rans_b_len  ][bytes rans_b  ]
  [u32 rans_r_len  ][bytes rans_r  ]
  [quad_tree_descriptor: depth-first traversal, var-length]
  ```
- **NAL escaping:** insert `0x03` after any `0x00 0x00 0x00`/`0x01`/`0x02`/`0x03` per ISO/IEC 14496-10 §7.4.1.1.
- **Evidence:** REQ-013, REQ-014.

#### 7.1.11 `RateController`
- **Purpose:** Translate profile (lossless / lossy:low / lossy:high / streaming-tight) into runtime knobs: filter strength, motion thresholds, top-list refresh interval, lossless vs lossy interpolation policy.
- **Evidence:** REQ-012.

### 7.2 Decoder components

![Decoder components](diagrams/04_c4_l3_decoder.png)

*Figure 4 — Decoder pipeline. The decoder is the inverse of the encoder, with one extra component: `PixelInterpolator`, which uses the cached previous frame and the per-region interlace pattern to fill scanlines that were not transmitted.*

#### 7.2.1 `SEIPayloadDemuxer`
Filters incoming NAL units, matches the SCC UUID, and unwraps NAL escaping. Returns the raw payload byte buffer.

#### 7.2.2 `FrameHeaderParser`
Parses width, height, bit-depth, mode flags, top_count, and top_values from the header.

#### 7.2.3 `rANS-8 Decoder` and `rANS-16 Decoder`
Inverse of the encoders. Renormalisation thresholds and probability tables MUST match bit-for-bit.

#### 7.2.4 `ListMerger`
For each pixel, reads `B[i,j]`. If `0`, indexes `TOP` by the next value in the rANS-8 stream. If `1`, takes the next int16 from the rANS-16 stream.

#### 7.2.5 `DisparityReconstructor`
Inverts the disparity transform via row-prefix sum:
```
d[1,1] = s[1,1]
for j = 2..W:    d[1,j]   = s[1,j]   + d[1,j-1]
for i = 2..H:
  for j = 1..W:  d[i,j]   = s[i,j]   + d[i-1,j]
```

#### 7.2.6 `QuadTreeRegionReader`
Re-builds the region map from the depth-first descriptor.

#### 7.2.7 `PixelInterpolator`
For each region whose interlace mask indicates skipped scanlines/pixels, interpolates skipped values from the cached previous frame using one of three strategies, profile-selectable:
- `prev` — reuse the previous frame's depth value at that coordinate (cheapest; banding under fast motion).
- `bilinear-temporal` — weighted blend with the previous frame.
- `edge-aware` — bilinear within the region but clamped at depth-edge boundaries detected via Sobel on the partial reconstruction.

The default for lossless is `prev` (no skipping in lossless); for lossy, `edge-aware`.

#### 7.2.8 `FrameCache`
Two-frame ring buffer (current and previous). The decoder MUST hold a stable reference until the consumer (renderer) has finished reading.

#### 7.2.9 `DepthOutputFormatter`
Repacks the reconstructed `int16` depth into the format the consumer wants:
- `R32F` — 32-bit float (WebGPU-friendly, normalised to [near, far]).
- `R16U` — 16-bit unsigned integer (closest to native sensor format).
- `R8U` — 8-bit (preview / thumbnail use only).

## 11. Security Architecture

### 11.1 Threat model

![STRIDE DFD](diagrams/15_threat_model.png)
*Figure 17 — STRIDE-aligned trust-boundary DFD. Three trust zones: untrusted internet (CDN, SFU), semi-trusted application tier (API, agent), trusted data tier (PostgreSQL, S3, KMS).*

#### Trust-boundary crossing analysis

| Crossing | S | T | R | I | D | E | Mitigation |
|---|---|---|---|---|---|---|---|
| User → CDN/API | ✓ | ✓ | ✓ | ✓ | ✓ |   | TLS 1.3, signed FE bundle, JWT (RS256), audit log on `auth.*`, WAF |
| User → SFU | ✓ | ✓ |   | ✓ | ✓ |   | DTLS-SRTP, ICE consent freshness |
| Sensor → Agent (USB) | ✓ |   |   |   | ✓ |   | OS-level USB permissioning; no remote attestation possible |
| Agent → SFU | ✓ | ✓ | ✓ | ✓ | ✓ |   | mTLS-over-QUIC; agent presents per-tenant client cert |
| API → Agent | ✓ | ✓ | ✓ | ✓ |   | ✓ | TLS + JWT + Unix-socket peer-cred check |
| API → RDS / S3 / KMS | ✓ | ✓ | ✓ | ✓ |   |   | IAM-role-based, SigV4, KMS audit |

### 11.2 Identity & access management
- **Users** stored in `users` table; roles `tenant_admin` / `operator` / `viewer`.
- **Service identities** via IAM roles for ECS tasks and EC2 instances. No long-lived access keys.

### 11.3 Authentication mechanisms
- **Human users:** email + Argon2id password OR SSO via OIDC (Auth0 / Okta — pluggable). MFA via TOTP.
- **Service users:** API key (32-byte URL-safe random), bound to tenant + scopes.
- **Agent:** mTLS client cert issued at registration, rotated every 90 d.

### 11.4 Authorisation model
- Coarse RBAC at the route level (Fastify `preHandler` hooks).
- Fine-grained tenancy isolation: every query includes `tenant_id`. Postgres Row-Level Security policies enforce this at the DB level as defence-in-depth.

### 11.5 Cryptography in use
- TLS 1.3 (ALB).
- DTLS-SRTP for media (mandated by WebRTC).
- AES-256-GCM at rest (S3 SSE-KMS).
- Argon2id for password hashing (libsodium).
- JWT signing: RS256.
- **No bespoke crypto in `libscc`.** The codec is plaintext; encryption is layered over by Kryotech or by tenants directly.

### 11.6 Secrets management
- **AWS Secrets Manager** for all service secrets.
- **No `.env` files in production.**
- Local `.env` files are git-ignored and contain only dev fixtures.

### 11.7 Input validation & output encoding
- API request bodies validated with `Zod` schemas; rejects on first error.
- The codec itself MUST validate every field of the SEI header (range checks on width/height, bit-depth ∈ {8, 12, 16}, top_count ∈ [2, 16]). Malformed payloads are rejected with `SCC_FORMAT`, never crash.
- The decoder MUST NOT trust width × height × bit-depth to size buffers without bounding the implied byte count to a configurable maximum (default 256 MiB).

### 11.8 Dependency security
- All C++ deps via Conan with locked versions and SHA-256 verification.
- All Rust deps via `Cargo.lock`; `cargo audit` in CI.
- All npm deps via `package-lock.json`; `npm audit --audit-level=moderate` in CI; Dependabot enabled.
- All Python deps via `poetry.lock`; `pip-audit` in CI.
- **SBOM** generated as CycloneDX JSON for every release artefact.

### 11.9 Transport & network security
- TLS 1.3 minimum.
- HSTS preload-eligible (`max-age=63072000; includeSubDomains; preload`).
- CSP: `default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; connect-src 'self' wss://… https://…; img-src 'self' data:; object-src 'none';`.
- CORS: `Access-Control-Allow-Origin` is _never_ `*` on authenticated routes.

### 11.10 Logging, audit, monitoring
- **Structured logs** (JSON) via Pino (Node) and `tracing` (Rust).
- **Auth events** (login success / failure / token issuance / mTLS rotation) emitted to a dedicated audit log indexed in Loki.
- **Metrics** via OpenTelemetry → Grafana.
- **Errors** to Sentry.

### 11.11 Compliance posture
- The product targets GDPR (operator data) and is designed to be deployable in PCI-DSS-adjacent environments without scope contamination — the codec does not handle cardholder data.
- **No claim of certification is made by this document.**

### 11.12 Known security gaps (forward-looking)
| ID | Gap | Severity | Recommendation |
|---|---|---|---|
| S-01 | Webhook HMAC not in MVP | Medium | Defer to v1.1; document signing scheme now to avoid breaking change. |
| S-02 | No formal threat model exercise yet (this DFD is a sketch). | Medium | Run a one-day STRIDE workshop before code freeze. |
| S-03 | No fuzzing harness for the SEI parser yet. | High | Add libFuzzer/AFL++ harness in CI before public release. |

## 14. Quality & Testing

### 14.1 Test strategy

Five tiers:

1. **Unit tests** (Catch2, pytest, Vitest, `cargo test`) — every component has tests. Encoder/decoder round-trip is the headline unit test.
2. **Property-based tests** (rapidcheck for C++, hypothesis for Python) — for the disparity transform (`forall depth: decode(encode(depth)) == depth` in lossless mode), for rANS round-trip, for the quad-tree builder.
3. **Integration tests** — end-to-end RGB-D → H.264+SEI → decode → reconstructed depth, plus interop with NVENC, QSV, VideoToolbox, MediaCodec.
4. **Codec benchmarks** — vs JPEG 2000, PNG, TIFF, zlib (mandatory comparators per **REQ-024**). See §14.2 and `acceptance/Test_Plan.md`.
5. **Fuzz testing** — libFuzzer harness against `scc_decode_sei`. Runs in nightly CI.

### 14.2 Codec benchmark harness

A separate `scc-bench` binary loads a corpus of depth sequences (single-camera and multi-camera per **REQ-023**) and reports, for each profile and each comparator:

- compression ratio (vs raw 16 bpp),
- encode and decode throughput (fps),
- per-frame PSNR and SSIM on reconstructed depth,
- visual regression: render reconstructed depth as a point cloud and capture canonical viewpoints; compare to reference PNGs (per **REQ-019**, the rotation/zoom artefact test).

The corpus includes at least: an Azure Kinect indoor scene, a RealSense D455 outdoor scene, a Stereolabs ZED2i stereo pair, and a synthetic depth dataset (NYU Depth v2 subset, public licence permitting).

- `clang-tidy` + `cppcheck` for C++.

## 15. Risks & Technical Debt

| ID | Description | Evidence | Severity | Recommendation |
|---|---|---|---|---|
| R-01 | rANS implementation correctness — renormalisation off-by-one is the canonical failure mode. | Duda 2014, §3.3; community implementations (ryg_rans) document this. | High | Adopt or generate test vectors against ryg_rans early; lock with property tests before any production use. |
| R-02 | H.264 hardware decoders may strip unrecognised SEI types. | ISO/IEC 14496-10 §7.4.2.4 (decoders may discard). Empirical evidence varies. | High | Test matrix across NVENC/QSV/VT/MediaCodec/libavcodec at MVP gate. Provide a fall-back "external SEI sidecar file" for environments where the SEI is stripped. |
| R-03 | Patent jurisdictional coverage — granted in US only. | US10827161B2 priority data. | Medium | Counsel review (DLA Piper, Dentons) for international prosecution decisions. |
| R-04 | PSNR/SSIM are imperfect proxies for "rotation/zoom artefact-free" reconstruction (REQ-019). | Industry literature on point-cloud quality metrics. | Medium | Add a render-and-diff visual regression test using canonical 3D viewpoints. |
| R-05 | Quad-tree leaf size 16×16 is a default; some scenes (very high-frequency depth) may warrant 8×8. | ADR-003. | Low | Make leaf size profile-tunable; default stays 16. |
| R-06 | WebGPU support is still uneven across browsers. | MDN compatibility tables. | Low | Provide a WebGL2 fallback render path in v1.1. |
| R-07 | Sensor SDK licensing — librealsense (Apache 2.0), K4A (MIT) are permissive; Stereolabs has commercial-only redistribution. | Vendor licence terms. | Medium | Restrict the bundled Stereolabs adapter to opt-in, and document the licensing constraints in `LICENSE-third-party.md`. |
| R-08 | NAL escaping correctness — easy to introduce a heisenbug here. | ISO/IEC 14496-10 §7.4.1.1. | Medium | Property tests + fuzzing on the round-trip `escape ∘ unescape == id`. |
| R-09 | Single-camera vs multi-camera evaluation may diverge sharply. | REQ-023 demands both. | Low | Bench corpus must contain both topologies from day one. |

No "generic" risks have been added. Every entry traces to a specific source.

3. **Phase C (weeks 9–12):** Decoder; lossy mode; movement detection; quad-tree; pixel interpolation.
4. **Phase D (weeks 13–16):** SDK bindings (C ABI, WASM, Python); benchmark vs JPEG 2000 and TIFF; first internal alpha.
5. **Phase E (weeks 17–20):** Reference app (frontend, API, agent); Unity/Unreal plugins; security workshop; β.
6. **Phase F (weeks 21–24):** Hardening, fuzzing, docs, public release.
